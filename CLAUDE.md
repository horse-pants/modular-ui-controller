# modular-ui-controller

ESP32-S3 LED controller with a 320×480 LVGL touch UI, WS2812 multi-strip animations (driven by Espressif's `led_strip` component over RMT+DMA) with audio sync, and an AsyncWebServer + WebSocket web UI. Built on **Arduino** framework (NOT ESP-IDF).

**Critical, often forgotten after context compaction.**

- ✅ `D:\PlatformIO\Projects\...`

### Single-user project — no migration paths

This is the user's personal device. **Don't write NVS migration code, backwards-compatibility shims, deprecated-key fallbacks, or "preserve old settings" logic.** When a field renames or moves, just rename/move it — the user will reflash + reconfigure as needed.

## Project Overview

- **Framework**: Arduino (NOT ESP-IDF)
- **Board**: ESP32-S3-DevKitC-1 (`platformio.ini` env `esp32-s3-devkitc-1`)
- **Display**: 320×480 touch screen driven by LovyanGFX + LVGL v9
- **LEDs**: WS2812 multi-strip via `led_strip` (IDF 5 RMT + DMA), audio-reactive animations
- **Web UI**: AsyncWebServer + WebSocket (served from LittleFS)
- **OTA**: via `ESP32WifiSetup` library

## Web UI

- **Main control surface** is a Svelte app under `web_src/`, built to `data/web/` and served from LittleFS via `AsyncWebServer::serveStatic("/", LittleFS, "/web/")`. Assets are gzipped at build time and AsyncWebServer auto-detects the `.gz` siblings.
- **Build trigger**: `build_web.py` runs eagerly when SCons sees `buildfs` / `uploadfs` in the command line. Edit Svelte sources in `web_src/`; the filesystem build refreshes `data/web/` automatically.
- **Dev loop**: `cd web_src && npm run dev` proxies `/ws` (and the legacy `/led-config`, `/update`, `/setup`, `/logs` endpoints) to the device — set `ESP32_IP` in `vite.config.js` or via env var.
- **WebSocket protocol** between the Svelte UI and `WebUIManager`: inbound messages `connect`, `vu`, `white`, `brightness`, `animation`, `colour`; outbound `states` (control snapshot) and `animations` (list).
- **Routing**: a tiny path-based router in `stores.js` (`route` store + `navigate(path)` helper) switches between the main controller view and the LED Config view based on `window.location.pathname`. The device's `/led-config` route serves the same `index.html` so deep links work.
- **REST endpoints**: `GET /get-led-config`, `POST /save-led-config` (form-urlencoded, returns `{ok:true}` then triggers a restart), `POST /clear-led-state` (returns `{ok:true}`). The Svelte LED Config view renders the saved/cleared status screens itself — no server-side status HTML.

## Architecture

### Global managers (declared in `main.cpp`)

```cpp
extern UIManager*        g_uiManager;        // LVGL UI
extern WifiBootManager*  g_wifiBootManager;  // WiFi + boot UI wrapper
extern LEDManager*       g_ledManager;       // LED strips + animations
extern WebUIManager*   g_webUIManager;   // Web interface
extern OTAManager*     g_otaManager;     // Firmware updates
```

### Main loop pattern

`loop()` is a sequence of `Update()` calls — `lv_tick_inc`, `UIManager::update`, `WifiBootManager::update`, `LEDManager::update`, `WebUIManager::update`, `OTAManager::loop`. Don't inline logic between them; put work on the manager being invoked.

`setup()` initialises UI first, then network. If `WifiBootManager` enters setup mode (no saved WiFi), the LED + full UI init are skipped — only the boot screen is up. Keep this branch shape; the boot UI assumes LEDs aren't initialised yet.
